## Result

The v1.5.14.48 routing-forensics pass materially narrows the 14 public ownerless weapon records.

### 1. `WS` is explicitly a passive-skill namespace

`game_common/guncore/SkillDataHelper.pyc` static evidence:

- `is_passive(skill_code)` constants: `2`, `PS`, `WS`, `YC`
- `get_table_name(skill_code)` constants: `2`, `AS`, `PS`, `WS`, `YC`
- `get_table_name` names: `ACTIVE_TABLE`, `PASSIVE_TABLE`
- module constants: `active_skill_data`, `passive_skill_data`

Narrow conclusion:

> `WS####` codes are intentionally routed through the passive-skill lane, not a third hidden skill table.

`is_skill_exist` calls `get_table_name` and `DataMgr.common_data`, confirming the table-routing role.

### 2. No alternate helper/UI owner was found

`PassiveSkillHelper.get_passive_skill_name` statically references:

- `DataMgr`
- `common_data`
- `get`
- literal `passive_skill_data`
- literal `name`

`SkillDataHelper.get_skill_desc` statically references:

- `DataMgr`
- `PASSIVE_TABLE`
- `common_data`
- `get`
- literal `discription`

`WRGunInfoPart.update_fixed_skills` still references `PassiveSkillHelper.get_passive_skill_name`, `skill_code`, `skill_data`, `discription`, and an empty-string fallback.

No alternate UI-only skill owner or alternate table is evidenced.

### 3. `climp_skill_code` does not evidence code expansion/remapping

`GunCoreHelper.climp_skill_code(skill_code)` has:

- only variable `skill_code`
- only referenced global `SKILL_CODE_LEN`
- only scalar constant `0`
- no mapping globals
- no replacement/prefix strings
- no alternate skill IDs

This strongly supports a bounded clamp/slice interpretation, not expansion of short codes such as `WS2001` into a different modern passive ID. Exact opcode semantics remain intentionally unclaimed because the game opcode table is not locally trusted.

The exact `SKILL_CODE_LEN` value is still not recovered in this bundle because it is imported from `game_common.guncore.SkillConst` rather than assigned in `GunCoreHelper`.

### 4. `WEAPON_TO_PASSIVE` and `WEAPON_PASSIVE_TO_SKILL_DAMAGE_CONFIG` are not hardcoded translation maps

The module-level constant pool for `CompShootDamageSimulateClient.pyc` contains the global names:

- `WEAPON_TO_PASSIVE`
- `WEAPON_PASSIVE_TO_SKILL_DAMAGE_CONFIG`
- `gun_blueprint_attr_data`
- `passive_skill_damage_simulate_data`

But it contains:

- no ownerless `WS####` codes
- no weapon IDs for the 14 public ownerless records
- no alternate passive IDs that could form a static translation dictionary

Therefore those globals are runtime caches/indices, not a hardcoded `WS2001 -> alternate passive` conversion table.

`get_weapon_passive_skill_config` itself contains only the relevant field strings `blueprint_no` and `fixed_skill_code` plus ordinary small numeric constants; it contains no alternate passive-code literals.

No exact scalar occurrence for any of the 11 codes appears in `passive_skill_damage_simulate_data` or another structured table.

This independently agrees with the previous full NeoX scan.

## Current strongest interpretation

The game architecture itself treats `WS####` as passive-skill identifiers, but the 11 codes used by these 14 normal public weapon blueprints have no exact current `passive_skill_data` owner and no proven alternate table, normalization expansion, UI fallback, static remap, server-buff route, stardust route, or exact damage-simulation owner.

That makes these records look increasingly like **dangling/legacy fixed-skill references retained on otherwise normal public weapon blueprints**.

This is still a structural interpretation, not permission to claim the weapons have no player-facing mechanic. Do not publish community mechanic text as canonical evidence.
